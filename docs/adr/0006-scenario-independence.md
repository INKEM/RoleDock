# ADR-0006：场景独立

- 状态：已接受（P0）
- 关联：`docs/DEVELOPMENT_PLAN.md` §2、§10

## 背景

RoleDock 从学术场景方案提炼而来，但定位是通用开源框架。若把"工程/文献/验收"等场景概念并入核心，框架会被第一个场景锁死，其他场景（以及场景本身的变化）都要改核心。

## 决策

核心只解释通用对象与状态（角色、文档、代次、请求、产物）；职责内容、知识模板、输出结构与业务流程由角色包或应用层提供。核心不含任何业务角色名称、角色数量假设或学术对象，该约束由一致性测试持续强制。学术应用（如 `roledock-academic`）独立建仓，通过 SDK/CLI/MCP 接口使用 RoleDock 并安装自己的角色包，依赖方向恒为"应用 → RoleDock"，核心不反向导入场景模块。演示用的三角色示例包只是示例数据，与框架能力无关。

## 后果

- 正面：任意角色组织即插即用；场景演进不需要改核心；判定标准明确——场景应用若必须改核心才能表达需求，即通用抽象不足，应以独立扩展提案处理。
- 负面：场景通用功能（如周期调度）需要走扩展提案流程，不允许以领域名称悄悄进入核心数据模型。
